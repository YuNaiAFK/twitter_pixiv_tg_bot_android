Only record a bot pid that is alive, and find the bot when the pid file lies

Two faults in run-bot.sh, both hit in practice.

1. The pid file was written immediately after the background start, before the liveness check
   five lines later. A start that failed - here, because another instance held the single-instance
   lock - left its dead pid in the file.

2. `--stop` trusted that file. Reading a dead pid, it reported "not running" and left the real bot
   alive and holding the Telegram poll, so every subsequent start was refused by the lock and the
   only way out was a manual kill. That is exactly what happened: the running bot kept its pid
   while the file pointed at two successive dead attempts.

Changes:

  - the pid is written only after `kill -0` confirms the process is alive; a failed start removes
    the file and additionally reports the lock conflict explicitly, since that cause was only
    visible buried in the other instance's startup banner
  - `--stop` tries the pid file, then falls back to `pgrep`/`pkill` on the project's own
    bot.py path, so a stale or missing file no longer makes the bot unstoppable. The pattern is
    the full script path rather than a bare "bot.py" so an unrelated process is not caught.

Both are only in the Android copy; the Windows project is untouched.
