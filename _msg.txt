Start the Bot API server through proot, and find the rootfs where 5.x puts it

Two independent faults made this script unusable, both reported as the wrong thing.

1. The rootfs path. proot-distro 5.x keeps it at containers/<name>/rootfs; 4.x used
   installed-rootfs/<name>. Only the old path was checked, so the script reported
   "binary missing at ..." for a binary that existed. Both layouts are now tried, and
   PROOT_BASE can be overridden if a later release moves it again.

2. The binary cannot be executed directly. Its interpreter is /lib/ld-linux-aarch64.so.1 -
   Debian's glibc loader. Android has /system/bin/linker64 instead, so a direct run gives
   "cannot execute: required file not found", which reads like a missing file rather than the
   wrong loader. It must go through `proot-distro login`, which supplies the chroot's loader and
   libraries. The pid recorded is proot's, since that is what stays alive.

`--dir` is validated with realpath and the server refuses to start if it does not exist, so the
directory is created first, from Termux - which also makes it owned by the user the chroot runs
as. Its chroot path (/root/telegram-bot-api) is what gets passed, not the Termux path, because
/data/data/com.termux/... does not exist inside the container.

cmd_stop now also kills any telegram-bot-api that outlives proot. A survivor keeps the port
bound, and the next start then reports "port 8081 is already in use by something else" - which
points at a mystery process rather than at this script's own previous run.

The loopback is shared: measured from the Termux app, a listener started inside the chroot on
0.0.0.0:8099 accepted a connection from Termux, so the bot can reach 127.0.0.1:8081 from
outside. Note the measurement has to be made FROM THE TERMUX APP - a process started with
`su 10209` is in the SELinux domain u:r:magisk:s0, where socket creation fails with
PermissionError and the network looks broken when it is not. Three rounds of this investigation
went the wrong way for exactly that reason.
