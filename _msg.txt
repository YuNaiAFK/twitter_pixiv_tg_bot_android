Report a user stop as a stop, not as an expired archive link

Presses of stop during the official archive download were reported as
"官方歸檔沒有任何分段下載成功（下載連結可能已過期，請重新取得）". The link was fine.

Both conditions hold when a stop arrives before any bytes land: nothing has been written AND the
stop flag is set. The written == 0 branch was tested first, so it won and produced a wrong
diagnosis that sends the user to re-request an archive that was never broken. Measured on the
phone: stopped 0.09 s into a 114.3 MiB download, and the log blamed an expired link.

Fixed by testing the stop first when nothing was written:

    if stopped() and written == 0:
        return written
    if written == 0:
        raise ...下載連結可能已過期...

The written == 0 check still has to exist for the case it was written for - every range
failing on its own, with no stop, which means the URL really is dead. Returning 0 there would
let the caller send a 0-byte archive, which is why that branch was added originally.

Two checks added, testing the decision order behaviourally rather than by matching text, so a
future reordering is caught even if the comments change:

  - a user stop is not reported as an expired link
  - a genuine total failure still reports an expired link
